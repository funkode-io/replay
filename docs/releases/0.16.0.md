## Highlights

**Every event carries a lane, and the online Policy feed reads only the online one.**
`events.lane` is `online` for every event stored so far and every event appended through
`Cqrs::execute`. The sweep and the late-write lookup read online rows only, through two
partial indexes, so however large a bulk append is, the bulk lane
([ADR-0034](https://github.com/funkode-io/replay/blob/main/docs/adr/0034-a-bulk-append-reaches-policies-through-a-work-queue.md))
adds nothing to the rows they scan and nominates no stream through them.

The per-stream read is different. When a stream is nominated, it still reads that
stream's bulk rows, and they count against the poll's read budget. What it skips is
**delivery**: a Policy passes a bulk event the way it passes a row its stream filter
excludes, so its place advances and nothing fires. A stream that mixes online events with
a large bulk therefore takes as many reads to pass as it has rows.

Nothing changes for an existing deployment. No registration or setting changed, and
with no bulk append yet every stored event is online.

**A bulk append reaches the Policies that consume the bulk lane through a work queue**
(funkode-io/replay#302). `Cqrs::execute_bulk` runs a command as `execute` does — the
middleware chain, the load, the handler, inline projections — and appends its events
stamped `bulk`. The transaction that writes an event also inserts one row of
`policy_bulk_work` for it for each Policy registered on the bulk lane that tracks the
stream's type. A Policy
opts in at registration, with the same `react`:

```rust
builder.register_policy(
    RecordAccepted,
    PolicySettings::new().on_lanes(Lanes::Bulk), // or Lanes::Both
)
```

The Policy's leader runs a worker that claims the lowest batch of its rows
(`read_batch_size`) with `FOR UPDATE SKIP LOCKED`, reacts to each event in position
order, dispatches the commands grouped by target stream — one aggregate load per target
per batch — deletes the claimed rows and commits. A stream's events arrive in that
stream's order; nothing is ordered across streams. A Policy registered after a bulk
execution committed never receives it, whatever its `StartAt`. Online stays the default:
a Policy that does not call `on_lanes` behaves exactly as before.

**A bulk append commits in bounded segments** (funkode-io/replay#303). `execute_bulk`
consumes the handler's `handle_stream` as it writes and commits every
`bulk_segment_size` events (default 1000), each segment one transaction holding its
events, their inline-projection rows and their bulk work. Peak memory is one segment
whatever the size of the bulk, and a bulk holds back an online Policy or a projection
catch-up for no longer than one segment takes to write. **A bulk is not all or
nothing**: a failure rolls back the segment it is in and is returned, and the segments
before it stay committed with their work queued. The expected version is checked before
the first segment only.

**The bulk lane survives a failed reaction and a dead worker** (funkode-io/replay#304).
A command that fails for good on the bulk lane is parked as a dead letter for its
triggering event, and its row leaves the queue with the rest of the batch, so one bad
record never wedges an import. The claim transaction stays open while a batch dispatches,
so a worker that dies mid-batch releases it and the next claim delivers every row again:
at-least-once, as the online lane. `retry_dead_letter`, `retry_policy_dead_letters` and
`discard_dead_letter` work on a bulk dead letter unchanged.

`PolicyStatus` gains `bulk_pending: Option<i64>`, the Policy's bulk queue depth, so an
operator can watch an import drain; it is `None` for a Policy never registered on the bulk
lane. `PolicyStatusStore::list` now lists a Policy only on the bulk lane too, and a Policy
on both lanes once, with both views. Pending bulk work keeps a Policy `Working`.

**Adopting the bulk lane is opt-in, per command and per Policy.** The handler streams
instead of collecting, the command runs through `execute_bulk` followed by an ordinary
completion command, and the Policies that want the bulk gain a lane at registration;
their `react` does not change. The README's
[The bulk lane](https://github.com/funkode-io/replay/blob/main/README.md#the-bulk-lane)
walks through a file import before and after, and states the rules: per-stream order
only, idempotent reactions, and external facts in tables rather than events.

**Command middleware: code that runs around every command.** Register a
`CommandMiddleware` on `Cqrs` and it runs on every command `Cqrs` executes, an
application's and a Policy's alike: `before` (may stop the command or add to its
metadata), `before_commit` (inside the append transaction, may roll it back) and `after`
(observes the outcome). A middleware can answer **`Busy`** — not now — which a caller
sees as the new `ErrorKind::Busy`, and which a Policy **holds** on, retrying until it
runs, instead of parking a dead letter. Maintenance mode is a middleware answering
`Busy` in both hooks plus `PostgresEventStore::await_in_flight_commits()` in the switch:
no inline projection guard, no catch-up debt, no dead letters
([ADR-0035](https://github.com/funkode-io/replay/blob/main/docs/adr/0035-a-command-passes-through-middleware-before-it-runs-and-before-it-commits.md),
[ADR-0036](https://github.com/funkode-io/replay/blob/main/docs/adr/0036-a-busy-command-is-held-not-dead-lettered.md);
README, *Command middleware*). A `Cqrs` without middleware behaves exactly as before.

## Breaking changes

Five, all mechanical ([Migration: command middleware](#migration-command-middleware)):

| Change | Who it breaks |
| --- | --- |
| `EventStore::store_events_stream` takes a seventh argument, the append's `CommitGate`, and a fourth type parameter for it | Direct callers of `store_events_stream` (turbofish `::<S, _, _>` becomes `::<S, _, _, _>`), and every third-party `EventStore` implementation. `store_events` is unchanged. |
| `replay::ErrorKind` gains a variant, `Busy` | Every exhaustive `match` on `ErrorKind` |
| `DeadLetterRetry` gains a variant, `Busy` | Every exhaustive `match` on what `retry_dead_letter` returns |
| `DeadLetterRetrySummary` gains a public field, `reactions_busy` | A struct literal of it, or a destructuring pattern without `..` |
| `PolicyStatus` gains a public field, `bulk_pending` | A struct literal of it — a test fixture, say — adds `bulk_pending: None`. Code that only reads a status is unaffected. |

```diff
 PolicyStatus {
     name: "fee_policy".into(),
     lag: 0,
     // …
+    bulk_pending: None, // Some(n) for a Policy on the bulk lane with n rows queued
 }
```

`PolicySettings::on_lanes`, `Lanes`, `Cqrs::execute_bulk` and
`PostgresEventStoreBuilder::bulk_segment_size` are additions. `write_event` gains a
ninth argument, `p_lane text DEFAULT 'online'`. Every existing call, including
`append_event`, compaction and a process not yet rolled, passes eight and resolves to it
unchanged.

## New API

### `Cqrs::execute_bulk`

```rust
impl Cqrs<PostgresEventStore> {
    pub async fn execute_bulk<A: Aggregate>(
        &self,
        id: &A::StreamId,
        metadata: replay::Metadata,
        command: A::Command,
        services: &A::Services,
        expected_version: Option<i64>,
    ) -> Result<A, A::Error>;
}
```

Runs `command` as `execute` does, through the aggregate's `handle_stream`, and appends
its events on the bulk lane in segments. A handler that streams its events never builds
a `Vec`; one that only implements `handle` works too, through `handle_stream`'s default.

The README's [The bulk lane](https://github.com/funkode-io/replay/blob/main/README.md#the-bulk-lane)
uses a file import, whose every accepted record is a decision:

```rust
use futures::stream::{self, BoxStream, StreamExt, TryStreamExt};

impl Aggregate for Import {
    // `handle` as before, for the online commands.

    async fn handle_stream(&self, cmd: ImportCommand, svc: &ImportFiles)
        -> Result<BoxStream<'static, Result<ImportEvent, replay::Error>>, replay::Error>
    {
        match cmd {
            ImportCommand::ProcessFile { file } => Ok(svc
                .rows(&file) // a stream, never a Vec
                .map_ok(|row| ImportEvent::RecordAccepted { row })
                .boxed()),
            other => Ok(stream::iter(self.handle(other, svc).await?).map(Ok).boxed()),
        }
    }
}

// With the bulk Policies registered first (see `on_lanes` below): every segment
// committed, or the error of the segment that failed.
cqrs.execute_bulk::<Import>(&import_id, metadata.clone(), ImportCommand::ProcessFile { file }, &files, None)
    .await?;

// Completion, if anyone needs to know, is an ordinary online command.
cqrs.execute::<Import>(&import_id, metadata, ImportCommand::Complete, &files, None)
    .await?;
```

### `PolicySettings::on_lanes` and `Lanes`

```rust
pub enum Lanes { Online /* default */, Bulk, Both }

impl PolicySettings {
    pub fn on_lanes(self, lanes: Lanes) -> Self;
}
```

Only the registration changes; `react` is the same on both lanes. A bulk append queues
work only for the Policies registered when it commits, and a Policy is registered when
its runner drains or its bulk worker starts, not when the runner is built. On a fresh
database, `drain` the runner once before the first `execute_bulk`:

```rust
let runner = PolicyRunner::builder(cqrs.clone())
    .register_services::<Brand>(()) // the aggregate EnsureBrand dispatches to
    .register_policy(
        EnsureBrand,
        PolicySettings::new()
            .with_stream_filter(StreamFilter::for_stream_type::<Import>())
            .on_lanes(Lanes::Both), // records accepted in the UI online, file records through the queue
    )
    .build();
runner.drain().await?; // the bulk Policies are registered from here on
```

### `PostgresEventStoreBuilder::bulk_segment_size`

```rust
let store = PostgresEventStore::builder(pool)
    .bulk_segment_size(500) // or REPLAY_BULK_SEGMENT_SIZE; default 1000, clamped to at least 1
    .build()
    .await?;
```

### `PolicyStatus::bulk_pending`

`Option<i64>`: the rows of bulk work queued for the Policy and not yet reacted to. `None`
for a Policy never registered on the bulk lane.

### Command middleware

`es-replay`:

- `ErrorKind::Busy` (status `Temporary`) and `Error::busy(reason)`: not now, the same
  command may succeed later.

`es-replay-persistence`:

- `CommandMiddleware`, with the hooks `before`, `before_commit` and `after`, each
  defaulting to doing nothing; `Next` (`Continue`, `Busy(String)`, `Error(replay::Error)`)
  and `Outcome` (`Committed`, `Busy(&str)`, `Failed(&error)`).
- `CommandContext` (aggregate type, stream type, stream id, command type, metadata,
  `causation()`), `CommandContextMut` (what `before` gets: `insert_metadata`,
  `set_metadata`) and `Causation` (`policy()`, `event_id()`, `stream_id()`,
  `global_position()`, `depth()`).
- `Cqrs::with_middleware(m)`, registering after every middleware before it.
- `CommitGate`, the trait of the store's new argument, implemented by any
  `FnOnce() -> impl Future<Output = Next>`, and `OpenGate`, the gate that always
  continues; `Next::into_result`.
- `PostgresEventStore::await_in_flight_commits()`: wait until every append that asked its
  commit gate before the call began has committed or rolled back.
- `DeadLetterRetry::Busy` and `DeadLetterRetrySummary::reactions_busy`: a retry that met a
  busy command settled nothing and left the rows parked.

### Maintenance mode

```rust
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;

use futures::future::BoxFuture;
use replay_persistence::{
    CommandContext, CommandContextMut, CommandMiddleware, Next, PostgresEventStore,
};

#[derive(Clone, Default)]
pub struct MaintenanceMode {
    switched_on: Arc<AtomicBool>,
}

impl MaintenanceMode {
    /// Switch on, and return once no command that checked the flag off can still commit.
    pub async fn switch_on(&self, store: &PostgresEventStore) -> replay::Result<()> {
        self.switched_on.store(true, Ordering::SeqCst);
        store.await_in_flight_commits().await
    }

    pub fn switch_off(&self) {
        self.switched_on.store(false, Ordering::SeqCst);
    }

    fn check(&self) -> Next {
        if self.switched_on.load(Ordering::SeqCst) {
            Next::Busy("maintenance in progress".to_string())
        } else {
            Next::Continue
        }
    }
}

impl CommandMiddleware for MaintenanceMode {
    // Stops a command that arrives during maintenance before it reads anything.
    fn before<'a>(&'a self, _context: CommandContextMut<'a>) -> BoxFuture<'a, Next> {
        Box::pin(async move { self.check() })
    }

    // Stops one that checked just before the switch and has not committed yet.
    fn before_commit<'a>(&'a self, _context: &'a CommandContext) -> BoxFuture<'a, Next> {
        Box::pin(async move { self.check() })
    }
}

let maintenance = MaintenanceMode::default();
let cqrs = Cqrs::new(store.clone()).with_middleware(maintenance.clone());

maintenance.switch_on(&store).await?;   // the store is quiet: run the migration
// ... cqrs.execute(..) now fails with ErrorKind::Busy; Policies hold, park nothing
maintenance.switch_off();               // held Policies resume on their own
```

The flag above is one process's. Across a fleet, read it from a row on every check —
never a cached copy — so that `await_in_flight_commits` vouches for every process's
appends. dxp-data-loom's maintenance guard registered as an inline projection can be
removed once this is in place.

### Enriching metadata: the acting user

```rust
use futures::future::BoxFuture;
use replay_persistence::{CommandContextMut, CommandMiddleware, Next};

tokio::task_local! {
    /// Set by the request layer around the commands it executes.
    pub static ACTING_USER: String;
}

pub struct ActingUser;

impl CommandMiddleware for ActingUser {
    fn before<'a>(&'a self, mut context: CommandContextMut<'a>) -> BoxFuture<'a, Next> {
        Box::pin(async move {
            // A Policy's command acts for the Policy; an application's for the request's user.
            let acting_user = match context.causation() {
                Some(causation) => format!("policy:{}", causation.policy()),
                None => match ACTING_USER.try_with(Clone::clone) {
                    Ok(user) => user,
                    Err(_) => {
                        return Next::Error(replay::Error::unauthorized(
                            "a command needs an acting user",
                        ))
                    }
                },
            };
            // Every event the command appends carries it.
            match context.insert_metadata("acting_user", acting_user) {
                Ok(()) => Next::Continue,
                Err(error) => Next::Error(error),
            }
        })
    }
}

let cqrs = Cqrs::new(store).with_middleware(ActingUser);

ACTING_USER
    .scope(
        "alice".to_string(),
        cqrs.execute::<BankAccount>(&account_id, Default::default(), command, &(), None),
    )
    .await?;
```

Both are compiled and run, against Postgres and a real Policy runner, from
`persistence/examples/command_middleware.rs`.

## Migration: the event lane (0039–0041)

Run the migrations **before** rolling the processes. The new release's sweep filters on
`lane`, so it needs the column. The old release runs unchanged against the new schema.

| Migration | What it does | What it costs on a populated `events` |
| --- | --- | --- |
| `0039_event_lane` | Adds `lane TEXT NOT NULL DEFAULT 'online'`, a `NOT VALID` check on its values, and replaces `write_event` with the nine-argument form | Catalog-only. A constant default rewrites nothing in PostgreSQL 11+, and `NOT VALID` skips the scan. The statement takes `ACCESS EXCLUSIVE` on `events` only for an instant, but it has to **queue** for that lock behind every open transaction that touched `events`, and appends queue behind it while it waits. |
| `0040_online_sweep_index` | `CREATE INDEX CONCURRENTLY idx_events_online_global_position ON events (global_position) WHERE lane = 'online'` | Appends keep running. The build scans the table twice and waits for every transaction open at its start. Its size is about that of `idx_events_global_position_unique`, because every existing row is online. |
| `0041_online_late_write_index` | `CREATE INDEX CONCURRENTLY idx_events_online_commit_txid_position ON events (commit_txid, global_position) WHERE lane = 'online'` | The same, sized like `idx_events_commit_txid_position`. |

### Runbook for a large table

1. **Size it first.** Expect the two builds to take about as long as the two full
   indexes they mirror took, and to need about the same space again:

   ```sql
   SELECT pg_size_pretty(pg_relation_size('idx_events_global_position_unique')),
          pg_size_pretty(pg_relation_size('idx_events_commit_txid_position'));
   ```

2. **Bound the wait in 0039.** Make sure no long transaction is open on `events` (a
   long report, or a stuck `idle in transaction` session), or give the migration's role a
   `lock_timeout` so it fails and can be retried instead of blocking appends while it
   waits. Once it has the lock, it holds it for an instant.

3. **Let 0040 and 0041 run.** They run outside a transaction (`-- no-transaction`), one
   statement each, and appends continue throughout. Build time grows with the table, and
   neither build finishes until every transaction that was open when it started has
   ended.

4. **If a build fails** (cancelled, timed out or interrupted), rerunning stops at
   "relation already exists". This is deliberate, as for 0015. Check what was left
   behind:

   ```sql
   SELECT indisvalid FROM pg_index
    WHERE indexrelid = 'idx_events_online_global_position'::regclass;
   ```

   If it is `false`, the build failed: run
   `DROP INDEX CONCURRENTLY idx_events_online_global_position` and rerun the migration.
   If it is `true`, the index was built and the process died before sqlx recorded the
   migration. Record the version as applied rather than rebuilding it. The same applies
   to `idx_events_online_commit_txid_position` and 0041.

5. **Optional, afterwards: validate the check.** Every existing row holds the default,
   so the `NOT VALID` constraint is true already. To mark it valid, run this at any
   time. It scans the table but takes only a `SHARE UPDATE EXCLUSIVE` lock, so appends
   continue:

   ```sql
   ALTER TABLE events VALIDATE CONSTRAINT events_lane_known;
   ```

**Ongoing cost.** Each online append now writes two more index entries: one per partial
index, on top of the full indexes, which stay because uniqueness, ordered reads of the
whole log and the inline-projection catch-up still use them. A bulk-lane row is in
neither partial index.

## Migration: the bulk work queue (0042)

`0042_policy_bulk_work` creates two empty tables, so it costs a populated database
nothing but their creation:

- `policy_bulk_registrations (policy, tracked_stream_types, registered_at)` — the
  Policies on the bulk lane. A runner writes its Policy's row when its bulk worker
  starts. A Policy removed from the code keeps its row, and bulk appends keep queueing
  work for it: delete the row, and that Policy's rows of `policy_bulk_work`, to retire
  it. Its tracked stream types only ever widen: every replica that starts merges
  what it tracks into the row, so an older replica cannot narrow which Policies an append
  queues work for, and narrowing them is an `UPDATE` of the row by hand. Work queued for
  a type the leading worker does not track is deleted by it without being delivered. So
  when a release widens a bulk Policy's stream types, stop the older leaders before
  anything appends a bulk of a newly tracked type, or an older leader deletes that work.
- `policy_bulk_work (policy, global_position)` — pending work only. A row is deleted by
  the worker that reacted to it, so an idle queue is empty.

Run it before rolling the processes, as 0039–0041.

## Migration: command middleware

### `store_events_stream` takes a commit gate

**A direct caller** passes `OpenGate`, the gate that always continues, and adds one `_`
to its turbofish. Nothing else changes: the append runs no middleware and takes no lock,
as before.

```rust
// 0.15
store
    .store_events_stream::<BankAccount, _, _>(
        &account_id, stream_type, metadata, events, expected_version, sink,
    )
    .await?;

// 0.16
use replay_persistence::OpenGate;

store
    .store_events_stream::<BankAccount, _, _, _>(
        &account_id, stream_type, metadata, events, expected_version, sink, OpenGate,
    )
    .await?;
```

A caller of `store_events` changes nothing.

**A third-party `EventStore`** takes the gate and asks it once per append, after every
event and every inline projection write is in place and immediately before committing:
commit on `Next::Continue`, otherwise roll back and return `Next::into_result`'s error.

```rust
use replay_persistence::{CommitGate, EventSink};

fn store_events_stream<S, ES, Sink, Gate>(
    &self,
    stream_id: &S::StreamId,
    stream_type: String,
    metadata: replay::Metadata,
    domain_events: ES,
    expected_version: Option<i64>,
    sink: Sink,
    gate: Gate,
) -> impl Future<Output = Result<(), replay::Error>> + Send
where
    S: replay::EventStream,
    ES: TryStream<Ok = S::Event, Error = replay::Error> + Send,
    Sink: EventSink<S::Event> + Send,
    Gate: CommitGate,
{
    async move {
        let mut transaction = self.begin().await?;
        // ... insert the events and run the inline projections, as before ...

        // Last, so the gate has the final word. Returning early must roll back.
        gate.check().await.into_result()?;

        transaction.commit().await
    }
}
```

A store must also leave **no gap between the check and the commit**: once an operator
switches a rule on and waits, no append that checked the old rule may still commit
(ADR-0035). The Postgres store takes a shared lock before asking any gate whose
`always_continues()` is `false` and offers `await_in_flight_commits()` to take it
exclusively; a store that cannot give the guarantee documents the gap.

### `ErrorKind` has a `Busy` arm

An exhaustive `match` on `replay::ErrorKind` no longer compiles until it handles `Busy`.
It means *not now*: the command is not wrong and may succeed unchanged later. It is
`Temporary`, like `Unavailable`, but it is not a fault — do not page on it and do not
count it against a retry budget.

```rust
use replay::ErrorKind;

fn http_status(kind: ErrorKind) -> u16 {
    match kind {
        ErrorKind::NotFound => 404,
        ErrorKind::InvalidInput => 400,
        ErrorKind::Conflict => 409,
        ErrorKind::Unauthorized => 401,
        ErrorKind::Forbidden => 403,
        ErrorKind::BusinessRuleViolation => 422,
        ErrorKind::RateLimited => 429,
        ErrorKind::Unavailable => 503,
        // New: a command middleware said not now (maintenance mode, for one).
        ErrorKind::Busy => 503,
        ErrorKind::Internal => 500,
    }
}
```

A `match` with a `_` arm compiles unchanged, but check where `Busy` lands: an arm that
treats every unknown kind as an internal error would now report maintenance mode as a
fault.

### A dead-letter retry can be busy

`retry_dead_letter` can now return `DeadLetterRetry::Busy`: the replay met a command a
middleware answered `Busy` for, settled nothing, and left every row of the reaction parked
exactly as it was. Treat it as *not yet*, and retry once the middleware lets commands
through. A bulk `retry_policy_dead_letters` counts such reactions in the new
`DeadLetterRetrySummary::reactions_busy`, not in `reactions_still_failing`.

```rust
use replay_persistence::{DeadLetterRetry, DeadLetterRetrySummary};

match runner.retry_dead_letter(id).await? {
    DeadLetterRetry::Resolved => { /* archived */ }
    DeadLetterRetry::StillFailing => { /* still parked, with its fresh error */ }
    DeadLetterRetry::Superseded => { /* another writer parked it mid-replay */ }
    // New: maintenance mode, say. Nothing changed; retry later.
    DeadLetterRetry::Busy => { /* left parked as it was */ }
    DeadLetterRetry::NotFound => { /* nothing matched the id */ }
}

// A struct literal names the new field, or takes the rest from `Default`.
let expected = DeadLetterRetrySummary {
    reactions_resolved: 3,
    reactions_still_failing: 0,
    reactions_busy: 0,
};
let also = DeadLetterRetrySummary { reactions_resolved: 3, ..Default::default() };

// A destructuring pattern names it too, or ends with `..`.
let DeadLetterRetrySummary { reactions_resolved, reactions_still_failing, reactions_busy } =
    runner.retry_policy_dead_letters("deposit_fee").await?;
```
