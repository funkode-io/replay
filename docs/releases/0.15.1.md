# v0.15.1 — A catch-up never walks the whole log

> Draft release notes, kept in the repo so the upgrade lands with the release. The
> published release page is assembled from this file (`docs/agents/release.md`).

## Highlights

**An inline projection's catch-up no longer walks the whole events table to find where
it starts.** Its starting-point lookup was a cached prepared statement; after five
executions Postgres switched to a generic plan that walked
`idx_events_global_position_unique` from the start of the log, every round, for every
projection. The lookup is now a fenced, unnamed `MIN` over owed rows only, so a round
that owes nothing stops there. The seal and the gap pages are unnamed too, so they are
planned with the real values (replay#306, replay#307).

---

## Fixes

- **Catch-up starting point** (`persistence`): range read from the horizon on every
  execution, not just the first five. On a 4 000-event log, 99 catch-up rounds read
  about what they apply (≤ 4 400 index tuples) instead of 386 546.
- **Long transactions holding the horizon back**: rounds no longer walk the marked rows
  above the horizon.
- **Paging stays on `global_position`**, which keeps each stream's events in
  `stream_seq` order.

---

## Upgrade notes

- No migration, no new index, no API break: a drop-in patch.
- **Catch-up order is promised per stream only.** Within a stream, events reach
  `handle` in `stream_seq` order; no order across streams is promised (README,
  CONTEXT.md, ADR-0018 and ADR-0032 now say so). A handler that combines several
  streams must not depend on which stream's events arrive first. Delivery itself is
  unchanged.
