# v0.11.0 — A policy is core vocabulary

> Draft release notes, kept in the repo so the migration lands with the code that causes
> it. The published release page is assembled from this file (`docs/agents/release.md`).

## Highlights

**A policy is now declared against `es-replay` alone.** `Policy`, `Dispatch` and the new
`ObservedEvent` moved to the core crate, so *when this event happens, issue that command*
— a business rule — no longer needs the crate that also holds `Cqrs`, `PostgresEventStore`
and the runner. The runner, the feed, the cursor, dead letters and every tunable stay in
`es-replay-persistence`, which re-exports the three permanently.

**`react` sees the four fields a rule may read.** `ObservedEvent<E>` carries `data`,
`stream_id`, `metadata` and `created`. `PersistedEvent` embeds it and derefs to it, so
`event.data` and friends read through unchanged everywhere else.

**Every knob is reachable from a closure policy.** The six tunables left the trait for a
`PolicySettings` value given at registration — `stream_filter`, `start_at`,
`read_batch_size`, `checkpoint_batch_size`, `dispatch_timeout` and `max_causation_depth`.
`register_policy_fn` used to take `start_at` and nothing else; the other five were
unreachable from a closure.

**A single-target policy declares its target.** `AggregatePolicy` names the aggregate as
an associated type and returns `(StreamId, Command)` pairs, so a unit test asserts the
reaction with `==` instead of downcasting a `Dispatch`. A blanket impl supplies `Policy`,
so the runner and `register_policy` are unchanged — and a type implements one trait or
the other, never both. A reaction that addresses several aggregate types stays a raw
`Policy` ([ADR-0028](https://github.com/funkode-io/replay/blob/main/docs/adr/0028-a-single-target-policy-declares-its-target.md)).

Both moves are recorded in
[ADR-0027](https://github.com/funkode-io/replay/blob/main/docs/adr/0027-the-policy-rule-is-core-vocabulary.md);
the decisions behind them are in [#244](https://github.com/funkode-io/replay/issues/244).

## Breaking changes

- `Policy::react` takes `&ObservedEvent<Self::Event>` instead of `&PersistedEvent<..>`.
- `Policy` no longer has `stream_filter`, `start_at`, `read_batch_size`,
  `checkpoint_batch_size`, `dispatch_timeout` or `max_causation_depth`.
- `PolicyRunnerBuilder::register_policy` takes a second argument, `PolicySettings`;
  `register_policy_fn`'s `StartAt` argument is replaced by one.
- `PersistedEvent`'s four observed fields moved into an embedded `ObservedEvent`, so a
  flat struct literal no longer compiles — nest them. Reads are unchanged (`Deref`).
- A policy no longer sees the triggering event's `id`. Idempotency comes from the
  command's shape, keyed on an identifier the triggering event carries.

No shim accepts the old envelope: it would reintroduce the dependency the move removes.

## New API

- `replay::ObservedEvent<E>` — `of`, `with_created`, `with_metadata`, and four public
  fields.
- `replay::Dispatch::into_parts::<A>()` — takes the `(StreamId, Command)` pair out of a
  dispatch, for an executor that runs it. Returns the dispatch unchanged when it targets
  another aggregate.
- `replay_persistence::PolicySettings`.
- `PersistedEvent::into_data()` — the payload, moved out of the envelope.
- `replay::AggregatePolicy` — `type Target`, a `react` returning `TargetedCommand`
  pairs, and a `dispatch_metadata` hook run once per reaction. Re-exported from
  `es-replay-persistence`; not in either prelude, so that a single-target test can call
  `policy.react(&event)` without `Policy`'s `react` making it ambiguous.
- `PolicyRunnerBuilder::register_aggregate_policy_fn` and
  `register_aggregate_policy_fn_with_metadata` — the closure registration with a declared
  target.

`es-replay` gains a chrono dependency, with no default features: `created` is a
type-level use with no clock call, and the crate still builds for `wasm32-unknown-unknown`.

## Migration

Four mechanical edits per policy.

**1. Envelope type** — `PersistedEvent` → `ObservedEvent` in the `react` signature and in
any helper the reaction shares:

```rust
use replay::{Dispatch, ObservedEvent, Policy};   // all three now come from the core crate

fn react(&self, event: &ObservedEvent<BankAccountEvent>) -> Vec<Dispatch> { … }
```

**2. `react` body** — `event.data`, `event.stream_id`, `event.metadata` and
`event.created` are unchanged. `event.id`, `event.version`, `event.r#type` and
`event.aggregate_version` are gone; a reaction that keyed idempotency on `event.id` keys
it on the operation's own identifier instead, carried by the event:

```rust
// BankAccountEvent::Deposited { amount, reference }
FeeLedgerCommand::ChargeFee {
    amount,
    charge_key: format!("{}#{reference}", event.stream_id),
}
```

Nothing in the envelope substitutes for that identifier. `created` in particular is not
one: Postgres stamps it from `now()`, which is transaction-stable, so every event of one
append shares it and two equal operations would collide. If the triggering event carries
no identity of its own, add one — it is domain data, and the rule has to see it.

**3. Tunables** — delete the overrides from the `impl Policy` block and state them at
registration:

```rust
use replay_persistence::{PolicySettings, StartAt, StreamFilter};

PolicySettings::new()
    .starting_at(StartAt::Beginning)
    .with_stream_filter(StreamFilter::for_stream_type::<BankAccount>())
    .with_read_batch_size(500)
    .with_checkpoint_batch_size(100)
    .with_dispatch_timeout(Duration::from_secs(90))
    .with_max_causation_depth(5)
```

Defaults and resolution order are unchanged: a setting given here wins, then the
environment variable, then the built-in default.

**4. Registration call** — both paths take the settings:

```rust
PolicyRunner::builder(cqrs)
    .register_services::<FeeLedger>(fee_services)
    .register_policy(FeePolicy { ledger_id }, PolicySettings::new().starting_at(StartAt::Beginning))
    .register_policy_fn::<BankAccountEvent, _>(
        "deposit_fee",
        PolicySettings::new().starting_at(StartAt::Beginning),
        |event| { … },
    )
    .build();
```

A `PersistedEvent` built as a **fixture** uses `PersistedEvent::of(stream_id, data)` and
its withers instead of a flat struct literal. A custom `EventStore` keeps its literal and
nests the four observed fields:

```rust
PersistedEvent {
    id: row.get("id"),
    r#type: row.get("type"),
    version: row.get("version"),
    aggregate_version: row.get("aggregate_version"),
    observed: ObservedEvent { data, stream_id, metadata, created },
}
```

`of` is for fixtures only — it mints an id, a version of 1 and `Utc::now()`, none of which
a store may invent for a row it read.

## Changes since 0.10.0

- `feat(es)`: a single-target policy declares its target in the type system (#239)
- `feat(es)!`: the policy rule moves to `es-replay`; the runner and its knobs stay in persistence (#237)
- `feat(persistence)!`: a policy tracks its position per stream (#231)
- `feat(persistence)`: build a `PersistedEvent` from the two fields a test cares about (#242)
- `feat(persistence)`: a dispatch hands back the pair it carries (#241)
- `fix(persistence)`: let the loser of a stream-creation race append (#235)
- `fix(persistence)`: settle a reaction a page at a time, under its own lock (#233)
- `fix(persistence)!`: a parked command is one row, whatever redelivers its event (#227)
