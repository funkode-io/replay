# v0.11.0 — upgrade guide

> Draft release notes, kept in the repo so the migration lands with the code that causes
> it. The published release page is assembled from this file (`docs/agents/release.md`).

This is an upgrade **runbook**, not a changelog. It assumes you are on `0.10.0` with a
populated database and a running fleet, and it is meant to be executable top to bottom by
a person or an agent. Read [§0](#0-pre-flight) through [§3](#3-code-migration) before you
start: two of the twenty-one migrations need a maintenance window, and one of them
(`0034`) must run with policy workers **stopped**.

| | |
| --- | --- |
| Scope | 37 PRs, 21 schema migrations, 7 breaking API changes (§3.1–§3.7), 6 silent behaviour changes (§4) |
| PostgreSQL floor | **13 → 15** — a hard gate, migration `0030` will not parse on 14 |
| Maintenance windows | 2 (`0027`, `0034`) — `0027` rewrites every row of `events`; `0034` scans it once per policy |
| Policy re-processing risk | none, **if** `0034` runs with workers stopped ([§2.4](#24-window-2--0034_policy_stream_cursors)) |
| Event data rewritten | `events.stream_seq` backfilled on every row (`0027`) |
| Data merged/lost | duplicate panic dead letters collapsed (`0029`) — [§2.3](#23-dead-letter-dedupe--0029--0030) |

---

## Highlights

**A policy is declared against `es-replay` alone.** `Policy`, `Dispatch` and the new
`ObservedEvent` moved to the core crate, so *when this event happens, issue that command*
— a business rule — no longer needs the crate that also holds `Cqrs`, `PostgresEventStore`
and the runner. `es-replay-persistence` re-exports all three permanently, so import paths
keep working.

**A policy tracks its position per stream, not per log.** `policy_cursors.position` — one
global watermark — became `policy_stream_cursors (policy, stream_id, stream_seq)`. A slow
or rolled-back write now delays the one stream it touches instead of stalling every policy
in the deployment behind a hole in the global sequence ([#231](https://github.com/funkode-io/replay/issues/231), ADR-0026).

**A worker that dies is now observable and restarted.** Panic containment, a restart
budget with backoff, an escalation hook, a dispatch timeout, a bounded stream-lock wait, a
durable heartbeat and edge-triggered narration logging all arrive in this release. On
`0.10.0` a panicking reaction killed its worker silently and a hung command handler was
indistinguishable from an idle policy.

**A parked command is one row.** Dead letters are unique per
`(policy, event, aggregate, target stream, command, ordinal)`; a redelivery refreshes that
row instead of adding a sibling (ADR-0024).

**A single-target policy can declare its target.** `AggregatePolicy` names the aggregate
as an associated type and returns `(StreamId, Command)` pairs, so a unit test compares the
reaction with `==` instead of downcasting a `Dispatch`. A blanket impl supplies `Policy`,
so the runner and `register_policy` are unchanged. Additive: a reaction that addresses
several aggregate types stays a raw `Policy`, and nothing forces an existing policy to
move ([ADR-0028](https://github.com/funkode-io/replay/blob/main/docs/adr/0028-a-single-target-policy-declares-its-target.md)).

## 0. Pre-flight

```sh
# 1. PostgreSQL 15 or newer — on 14 or older, migration 0030 fails to parse.
psql -c "show server_version"

# 2. Back up. 0027, 0029 and 0034 rewrite or merge rows; re-running the set does not undo them.
pg_dump ...

# 3. Confirm no duplicate global_position (hand-inserted or copy-restored rows).
#    Migration 0014 runs this check itself and refuses the whole run if it fails.
SELECT global_position, count(*) FROM events GROUP BY global_position HAVING count(*) > 1;

# 4. Size the two windows. `0027` rewrites every row of `events` inside one
#    transaction, so the table's on-disk size is the number that matters, not just
#    the row count.
SELECT count(*) AS events, pg_size_pretty(pg_total_relation_size('events')) AS on_disk
  FROM events;                                  -- 0027 rewrites all of it
SELECT count(*) FROM policy_cursors;            -- 0034 scans `events` once per policy
SELECT count(*) FROM policy_dead_letters;       -- 0028/0029 scan the parked backlog
```

**PostgreSQL floor.** 13 gave `xid8` (`0018`); 15 gives `NULLS NOT DISTINCT`, which is what
keeps a parked dead letter unique over an identity that is nullable for a reaction with no
dispatch to name (`0030`). 13 left upstream support on 13 November 2025; 14 leaves it on
12 November 2026. On 14, `0030` is a parse error — the run stops there, it does not
silently degrade.

## 1. Ordering: what must happen in what order

Every ordering constraint in this release is one constraint wearing three hats: **no
`0.10.0` process may be running against a schema it has been migrated past.** No migration
here requires the new code to have run first. So the simplest correct upgrade is also the
recommended one.

### 1.1 Recommended: stop the world

```
stop every process (app, workers, compaction jobs)
  → run migrations 0014–0034 in order
  → start 0.11.0
```

This satisfies `0027`'s "quiesce writers", `0030`'s "no old parkers" and `0034`'s "policy
daemons stopped" simultaneously, and it is the only arrangement in which `0034`'s backfill
is exact rather than merely careful — see [§2.4](#24-window-2--0034_policy_stream_cursors).

Three things it does not solve:

- **Ten migrations cannot run inside a transaction.** `0015`, `0016`, `0017`, `0019`,
  `0020`, `0021`, `0026`, `0030`, `0031` and `0032` carry `-- no-transaction` on line 1 and
  are `CONCURRENTLY` index work. A runner that wraps each migration in a transaction by
  default fails these with `CREATE INDEX CONCURRENTLY cannot run inside a transaction
  block`. The directive is an sqlx convention; map it onto your runner before you start.
- **Size the window from `0027`, not from the migration count.** On `events` a
  stop-the-world run does: one scan for `0014`'s guard; two passes each for `0015`, `0019`
  and `0020`'s concurrent builds (buying an online-ness a stopped fleet is not using); then
  `0027` — a **full rewrite of every row**, plus a sort for the window function, a
  `GROUP BY` rollup into `streams`, a `SET NOT NULL` validation scan and a non-concurrent
  unique index build, all in one transaction; then one scan per policy for `0034`. The
  rewrite dominates: it writes a new tuple version for every event, so budget WAL and
  on-disk growth of roughly one extra copy of `events` until the follow-up vacuum.
- **`0027` is a single transaction.** Anything that kills it mid-way rolls back the whole
  renumber. Set `statement_timeout = 0` and `idle_in_transaction_session_timeout = 0` on
  the migration session.

### 1.2 Alternative: staged, without a full stop

Only if a stop-the-world window is impossible. Read `0030` in
[§2.3](#23-dead-letter-dedupe--0029--0030) first: a `0.10.0` policy worker is **not**
safe to leave running once `0030` exists.

| Step | Action | App / append traffic | Policy workers |
| --- | --- | --- | --- |
| 1 | Migrations `0014`–`0026` | up, `0.10.0` | up, `0.10.0` |
| 2 | **Window 1**: migration `0027` | **quiesced** (incl. compaction) | quiesced |
| 3 | Migration `0028` | up | up |
| 4 | **Stop all policy workers** | up | **stopped** |
| 5 | Migrations `0029` + `0030` | up | stopped |
| 6 | Migrations `0031`–`0033` | up | stopped |
| 7 | Deploy `0.11.0` | rolling OK | **stay stopped** |
| 8 | **Window 2**: migration `0034` | up | stopped |
| 9 | Start policy workers on `0.11.0` | up | up, `0.11.0` |

Policy workers are down from step 4 to step 9 — across the `0030` build, the deploy and
`0034`. **If your workers share a process with the application, that process is down for
that span too**, and the staged path buys you nothing over §1.1.

**`PolicyStatusStore::list()` also fails between step 7 and step 8.** The `0.11.0` query
selects `policy_cursors.discovered_through` and joins `policy_stream_cursors`, neither of
which exists until `0034`. Appends, commands and event queries keep working, but a status
or monitoring endpoint built on `list()` returns an error for that gap — expect the alert
and do not treat it as a failed deploy.

The three orderings that are not negotiable:

- **`0027` before the `0.11.0` deploy.** New-code `compact` calls a `write_event` an
  un-migrated database does not have.
- **`0030` before any `0.11.0` park, and after the last `0.10.0` one.** Neither binary is
  safe on the wrong side of it ([§2.3](#23-dead-letter-dedupe--0029--0030)).
- **`0034` with workers stopped, on both sides of the deploy.** A `0.10.0` worker against
  the post-`0034` schema fails every poll (`position` and `commit_txid` are gone); a
  `0.11.0` worker against the pre-`0034` schema fails every poll too
  (`policy_stream_cursors` does not exist), and with no escalation hook installed the
  default action on an exhausted restart budget is `exit(70)`
  ([§4.4](#44-with-no-escalation-hook-the-process-exits)). Appends, commands and queries
  are untouched by `0034` and keep running.

## 2. Database migration

Apply the SQL in `persistence/tests/migrations/` in numeric order (despite the `tests/`
path, this is the deployment schema — `persistence/tests/common/migrations.rs`).

### 2.1 The cheap set — `0014`–`0026`, `0031`–`0033`

Cheap against the *database*: every index is built `CONCURRENTLY`, and every `ADD COLUMN`
uses a constant default or no default, so it is catalog-only on PostgreSQL 11+ and takes
its `ACCESS EXCLUSIVE` lock momentarily rather than rewriting the table.

Cheap is not the same as safe to run with old code up. `0014`–`0026` are; **`0031`–`0033`
are not**, because by then `0030` exists and a `0.10.0` policy worker conflicts on its own
second park ([§2.3](#23-dead-letter-dedupe--0029--0030)). In the staged path of
[§1.2](#12-alternative-staged-without-a-full-stop) policy workers are already stopped by
that point and stay stopped; the app itself is unaffected either way.

| Migration | What it does | Cost scales with |
| --- | --- | --- |
| `0014` | Refuses the run if `events.global_position` is not unique | one scan of `events`, read-only |
| `0015` | `CREATE UNIQUE INDEX CONCURRENTLY` on `global_position` | two passes over `events` |
| `0016` | Drops the superseded non-unique `global_position` index | — |
| `0017` | Drops `idx_events_policy_feed` — no plan has matched it since #93 | — |
| `0018` | `events.commit_txid xid8 NOT NULL DEFAULT '0'` — nothing reads it yet | catalog only |
| `0019` | Index `(commit_txid, global_position)` | two passes over `events` |
| `0020` | Index on `created`, for the time-travel filter only | two passes over `events` |
| `0021` | Drops the `(created, version, id)` keyset index — 50k rows: 3 056 kB → 1 112 kB, same plan (ADR-0018, ordered by `global_position`) | — |
| `0022` | `policy_cursors.commit_txid` — **dropped again by `0034`** | # policies |
| `0023` | `policy_cursors.last_beat_at/liveness/last_polled_at/led_by` | # policies |
| `0024` | `aggregate_name/target_stream_id/command_name` on both dead-letter tables | catalog only |
| `0025` | `retry_count/last_retried_at` on both dead-letter tables | catalog only |
| `0026` | Index `(policy_name, global_position, event_id, id)` — turns an O(N²) bulk retry linear | parked backlog |
| `0031` | Index `(policy_name, created_at DESC) INCLUDE (last_parked_at)` | parked backlog |
| `0032` | Drops the index `0031` replaces | — |
| `0033` | Replaces `write_event` so a lost stream-creation race defers instead of erroring | catalog only |

`0015` is deliberately not `IF NOT EXISTS`: a rerun after a failed concurrent build stops
loudly instead of leaving an invalid index. Recovery is in the file.

`0023` is the one migration explicitly declared deploy-order-agnostic. The four heartbeat
columns are consumer-owned: the runner writes them when they exist and **silently turns the
durable heartbeat off for the process lifetime when they do not** (Postgres `42703`, logged
once at `warn`). Add all four or none — a partial set disables the beat.

### 2.2 Window 1 — `0027_event_stream_seq`

Gives every event a second number: `stream_seq`, its place in its own stream, which
compaction never resets (ADR-0023). This is what the new per-stream cursors count in.

```sql
ALTER TABLE streams ADD COLUMN IF NOT EXISTS stream_seq BIGINT NOT NULL DEFAULT 0;
ALTER TABLE events  ADD COLUMN IF NOT EXISTS stream_seq BIGINT;

UPDATE events AS e SET stream_seq = numbered.seq
  FROM (SELECT id, row_number() OVER (PARTITION BY stream_id ORDER BY global_position) AS seq
          FROM events) AS numbered
 WHERE e.id = numbered.id AND e.stream_seq IS NULL;

UPDATE streams AS s SET stream_seq = numbered.last_seq
  FROM (SELECT stream_id, MAX(stream_seq) AS last_seq FROM events GROUP BY stream_id) AS numbered
 WHERE numbered.stream_id = s.id;

ALTER TABLE events ALTER COLUMN stream_seq SET NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS uidx_events_stream_seq ON events (stream_id, stream_seq);
CREATE OR REPLACE FUNCTION write_event(...)  -- compaction's snapshot insert folded in
```

**This is not an online migration.** One transaction takes `ACCESS EXCLUSIVE` on `streams`
in its first statement and on `events` in its second and holds both to the end, so the
backfill, the `NOT NULL` scan and the non-concurrent unique index build all block **readers
as well as writers**. A fleet looks stalled, not slow. Budget WAL and dead-tuple space of
about one table copy: the backfill writes a new tuple version for every event, so the
table roughly doubles on disk until it is vacuumed.

Inside that one transaction, `events` is walked four times — the window function's scan and
sort, the `GROUP BY stream_id` rollup into `streams`, the `SET NOT NULL` validation, and
the unique index build — on top of the rewrite itself. Sizing this from the row count alone
understates it; size it from `pg_total_relation_size('events')`.

**Quiesce writers, migrate, then deploy.** Two things fail if they overlap it — both
loudly, neither corrupting anything:

- An append already inside `append_event` when the migration commits keeps the function
  body it entered with, which writes no place, and its insert is refused. A command
  *issued* during the migration is fine: it waits, then calls the new function.
- Compaction from either side of a mixed fleet. An old process inserts snapshot rows naming
  no place, which the new `NOT NULL` forbids; a new process calls a function an un-migrated
  database lacks. Compaction is best-effort, so the next run after the rollout succeeds.

Ordinary appends from a `0.10.0` process are safe once `0027` has landed — `append_event`
keeps its signature and is numbered by the new function underneath it. Roll the fleet at
leisure.

### 2.3 Dead-letter dedupe — `0029` + `0030`

`0029` is the only migration in this release that **merges rows**. Run it and `0030` as one
unit with the policy daemons quiesced.

Phase 1 gives *ambiguous* rows — parked before `0024`, so naming no command — synthetic
negative `dispatch_ordinal`s so each is individually addressable. They are **not** merged:
the schema cannot prove they are duplicates rather than distinct commands, and retiring an
active failure on a guess is the one thing a dead letter must never do (ADR-0024).

Phase 2 collapses the one provable duplicate shape — `error_kind = 'Panic'` with every
identity column null, which a panicking reaction always produces:

```sql
-- the newest-parked row survives, carrying the group's aggregate
--   created_at    = min   last_parked_at  = max
--   deliveries    = sum   retry_count     = max
-- losers are DELETEd from policy_dead_letters and INSERTed into
-- discarded_dead_letters with reason = 'superseded'
```

**What you will observe after the upgrade:** `policy_dead_letters` row counts drop for any
policy that had a panic redelivered. The surviving row keeps the newest generation's error
text verbatim; older generations' error text survives only in the archive. Audit it with:

```sql
SELECT policy_name, event_id, count(*)
FROM discarded_dead_letters WHERE reason = 'superseded'
GROUP BY policy_name, event_id;
```

`0030` then builds the uniqueness key, `CONCURRENTLY` because the table is the daemon's
write path:

```sql
CREATE UNIQUE INDEX CONCURRENTLY idx_dead_letters_parked_command
    ON policy_dead_letters (policy_name, event_id, aggregate_name, target_stream_id,
                            command_name, dispatch_ordinal)
    NULLS NOT DISTINCT;   -- PostgreSQL 15
```

A concurrent build **fails** rather than blocks. If a `0.10.0` writer that did not actually
stop created a duplicate mid-build: drop the invalid index, re-run `0029`'s phase 1 by hand
(safe to repeat — it numbers below the lowest synthetic ordinal already used), then rebuild.

**A `0.10.0` policy worker is not safe to leave running once `0030` exists.** Its park is an
unconditional `INSERT` that supplies none of the identity columns — `aggregate_name`,
`target_stream_id`, `command_name` (added by `0024`, populated from #217) and
`dispatch_ordinal` (`0028`) are all null. Under `NULLS NOT DISTINCT` those nulls compare
equal, so the key collapses to `(policy_name, event_id)` for that binary: the **second**
row it tries to park for one event takes a `23505`, whatever produced it — a reaction
failing two commands, or `0.10.0` parking once per *attempt* rather than per delivery
(#212 is what changed that, and it is in this release). The poll fails, and only the first
failed command of that reaction is recorded.

So this is a hard cutover for policy workers, not a bounded rough edge. Stop them before
`0029`, keep them stopped through `0030`. (The migration's own header describes the
narrower case — re-parking a command the binary already parked — which understates it;
worth an upstream correction.)

**Dead letters parked under `0.10.0` stay retryable.** Rows with no identity columns are
settled all-or-nothing per replay, as they always were; rows parked with identity columns
match on `(aggregate, target stream, command)`.

### 2.4 Window 2 — `0034_policy_stream_cursors`

```sql
CREATE TABLE IF NOT EXISTS policy_stream_cursors (
    policy TEXT NOT NULL, stream_id TEXT NOT NULL, stream_seq BIGINT NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(), PRIMARY KEY (policy, stream_id));

INSERT INTO policy_stream_cursors (policy, stream_id, stream_seq)
SELECT pc.name, e.stream_id, MAX(e.stream_seq)
FROM policy_cursors pc JOIN events e ON e.global_position <= pc.position
GROUP BY pc.name, e.stream_id
ON CONFLICT DO NOTHING;

ALTER TABLE policy_cursors RENAME COLUMN position TO discovered_through;
ALTER TABLE policy_cursors DROP COLUMN IF EXISTS commit_txid;
ALTER TABLE policy_cursors ADD COLUMN IF NOT EXISTS reconciled_through TEXT NOT NULL DEFAULT '';
```

**Stop the policy daemons fleet-wide, migrate, then start them on `0.11.0`.** Appends and
command handling are untouched; only policy workers need to be down. The backfill joins the
whole log once per policy over an unindexed inequality, with no index on that predicate —
budget one sequential scan of `events`
multiplied by the number of registered policies. That join is why the window covers the
migration and not just the deployment.

**Will a policy re-deliver or skip events? Neither, exactly.** Each policy is seeded, per
stream, to the highest `stream_seq` that stream had reached *by the global position its old
cursor stopped at* — not to the stream's current head, and not to zero. Proven by
`persistence/tests/it/policy_cursor_backfill.rs`:

| Old cursor state | Backfilled to | Result |
| --- | --- | --- |
| Mid-log (e.g. global position 4 across two interleaved streams) | `stream_seq = 2` in each | resumes exactly where it was |
| A stream written entirely after the cursor's position | no row at all | absent cursor = start of stream, still owed every event |
| `position = 0` (never ran) | nothing seeded | starts every stream at the beginning, unchanged |
| `position = head` (caught up) | every stream's head | owed nothing, no re-delivery |

The one thing that breaks this is a worker still polling and writing `position` while the
migration runs. Hence the full stop.

`policy_cursors.commit_txid` (added by `0022` earlier in this same release) is dropped
permanently — policies no longer read a global order at all. `position` is **renamed**, not
redefined in place: `discovered_through` is a sweep hint, not progress. If you have tooling
that reads `policy_cursors.position` as "processed through", it must move to
`policy_stream_cursors.stream_seq`.

## 3. Code migration

### 3.1 `Policy`: five methods removed, `react` takes `ObservedEvent`

`Policy`, `Dispatch` and `ObservedEvent` now live in `es-replay`; `replay_persistence`
re-exports them, so either import path compiles.

```rust
// BEFORE (0.10.0)
use replay_persistence::{Dispatch, PersistedEvent, Policy, StartAt, StreamFilter};

impl Policy for FeePolicy {
    type Event = BankAccountEvent;
    fn name(&self) -> &str { "deposit_fee" }
    fn start_at(&self) -> StartAt { StartAt::Beginning }
    fn stream_filter(&self) -> StreamFilter { StreamFilter::for_stream_type::<BankAccount>() }
    fn read_batch_size(&self) -> Option<u32> { Some(500) }
    fn react(&self, event: &PersistedEvent<Self::Event>) -> Vec<Dispatch> { /* … */ }
}
```

```rust
// AFTER (0.11.0)
use replay::{Dispatch, ObservedEvent, Policy};
use replay_persistence::{PolicySettings, StartAt, StreamFilter};

impl Policy for FeePolicy {
    type Event = BankAccountEvent;
    fn name(&self) -> &str { "deposit_fee" }
    fn react(&self, event: &ObservedEvent<Self::Event>) -> Vec<Dispatch> { /* … */ }
}
```

`stream_filter`, `start_at`, `read_batch_size`, `checkpoint_batch_size`,
`max_causation_depth` and the new `dispatch_timeout` are supplied at registration instead —
a closure policy could never override a trait method, so five of the six knobs were
unreachable from `register_policy_fn`.

An override of a removed method is `error[E0407]`. Loud.

### 3.2 `ObservedEvent` is four fields, not eight

```rust
pub struct ObservedEvent<E> {
    pub data: E,
    pub stream_id: Urn,
    pub metadata: Metadata,
    pub created: DateTime<Utc>,
}
```

`event.data`, `event.stream_id`, `event.metadata` and `event.created` read unchanged inside
`react`. `event.id`, `event.version`, `event.r#type` and `event.aggregate_version` are gone
from the reaction's view — that is the point of the move: a rule must not key on the store's
identity for the triggering event.

A reaction that keyed idempotency on `event.id` keys it on the operation's own identifier,
carried by the event:

```rust
// BEFORE
FeeLedgerCommand::ChargeFee { amount, charge_key: event.id.to_string() }

// AFTER — BankAccountEvent::Deposited { amount, reference }
FeeLedgerCommand::ChargeFee {
    amount,
    charge_key: format!("{}#{reference}", event.stream_id),
}
```

Nothing in the envelope substitutes for that identifier. `created` in particular does not:
Postgres stamps it from `now()`, which is transaction-stable, so every event of one append
shares it and two equal operations would collide. If the triggering event carries no
identity of its own, add one — it is domain data, and the rule has to see it.

### 3.3 `PersistedEvent`: four fields moved under `observed`

```rust
pub struct PersistedEvent<E> {
    pub id: Uuid,
    pub r#type: String,
    pub version: i64,
    pub aggregate_version: Option<i32>,
    pub observed: ObservedEvent<E>,   // data, stream_id, metadata, created
}
impl<E> Deref for PersistedEvent<E> { type Target = ObservedEvent<E>; }
```

Reads and writes through field syntax are unchanged (`Deref`/`DerefMut`). What breaks is
**struct-literal construction** and **destructuring**:

```rust
// BEFORE — a hand-built test fixture
let event = PersistedEvent {
    id: Uuid::new_v4(), data: BankAccountEvent::Deposited { amount: 100.0, reference },
    stream_id: account_urn.clone().into(), r#type: "Deposited".into(),
    version: 1, created: Utc::now(), metadata: Metadata::default(), aggregate_version: None,
};

// AFTER — fixtures use the builder
let event = PersistedEvent::of(account_urn.clone(), BankAccountEvent::Deposited { amount: 100.0, reference })
    .with_version(1);
```

`of` mints an id, a version of 1 and `Utc::now()`, so it is for fixtures only. A custom
`EventStore` reading a row keeps its literal and nests the four fields:

```rust
PersistedEvent {
    id: row.get("id"), r#type: row.get("type"),
    version: row.get("version"), aggregate_version: row.get("aggregate_version"),
    observed: ObservedEvent { data, stream_id, metadata, created },
}
```

A consuming read of the payload needs the new method, since `.data` cannot be moved out
through a `Deref` target:

```rust
stream.apply(event.data);        // BEFORE
stream.apply(event.into_data()); // AFTER
```

### 3.4 Registration takes `PolicySettings`

```rust
// BEFORE
PolicyRunner::builder(cqrs)
    .register_policy(FeePolicy { ledger_id })
    .register_policy_fn::<BankAccountEvent, _>("deposit_fee", StartAt::Beginning, |event| { … })
    .build();

// AFTER
PolicyRunner::builder(cqrs)
    .register_services::<FeeLedger>(fee_services)
    .register_policy(
        FeePolicy { ledger_id },
        PolicySettings::new()
            .starting_at(StartAt::Beginning)
            .with_stream_filter(StreamFilter::for_stream_type::<BankAccount>())
            .with_read_batch_size(500)
            .with_checkpoint_batch_size(100)
            .with_dispatch_timeout(Duration::from_secs(90))
            .with_max_causation_depth(5),
    )
    .register_policy_fn::<BankAccountEvent, _>(
        "deposit_fee",
        PolicySettings::new().starting_at(StartAt::Beginning),
        |event: &ObservedEvent<BankAccountEvent>| { … },
    )
    .build();
```

Resolution order is unchanged: a setting given here wins, then the environment variable,
then the built-in default.

### 3.5 `DeadLetterRetry` gained `Superseded`

```rust
// BEFORE: Resolved | StillFailing | NotFound
// AFTER:  Resolved | StillFailing | Superseded | NotFound     (not #[non_exhaustive])
match runner.retry_dead_letter(id).await? {
    DeadLetterRetry::Resolved => { /* archived */ }
    DeadLetterRetry::StillFailing => { /* re-parked with its own error */ }
    DeadLetterRetry::Superseded => { /* another writer parked this while the replay ran:
                                        nothing was settled, retry again later */ }
    DeadLetterRetry::NotFound => { /* nothing to do */ }
}
```

The exhaustiveness error is loud — but reaching for `_ => {}` instead of an arm silently
folds "retry again" into "nothing to do". Handle it.

### 3.6 `DeadLetterRetrySummary`: renamed fields, and the unit changed

```rust
// BEFORE — counted rows
pub struct DeadLetterRetrySummary { pub resolved: usize, pub still_failing: usize }
// AFTER — counts reactions
pub struct DeadLetterRetrySummary { pub reactions_resolved: usize, pub reactions_still_failing: usize }
```

The rename is a compile error; the unit change under it is not. A reaction that parked two
commands used to contribute two to the count and now contributes one.
`PolicyStatus::dead_letter_count` still counts **rows**, so `dead_letter_count = 2` with
`reactions_still_failing = 1` is now a correct and expected pairing. Do not sum them into
one dashboard number.

### 3.7 `PolicyStatus`: `position` and `head` removed

```rust
// BEFORE
pub struct PolicyStatus { name, position, head, lag, last_checkpoint_at,
                          dead_letter_count, last_dead_letter_at, condition }
// AFTER
pub struct PolicyStatus { name, lag, streams_behind, discovered_through, last_checkpoint_at,
                          dead_letter_count, last_dead_letter_at, condition }
```

`.position` and `.head` fail to compile. `.lag` does not — see [§4.1](#41-policystatuslag-is-a-different-number).

`PolicyCondition` is `CaughtUp | Working | Degraded`, same as `0.10.0`.

**Why this list is shorter than the README's.** The README's breaking note says
`PolicyStatus` lost `position`, `head`, `next_position` and `missing_position`, and
`PolicyCondition` lost `Blocked`. It is written relative to the state just before the
per-stream cursor landed, not relative to `0.10.0`. `next_position`, `missing_position` and
`Blocked` were all added by #172 and removed again by #231 — both inside this release
window — so coming from `0.10.0` they never existed for you and there is nothing to
migrate. Only `position` and `head` are removals you can actually hit.

### 3.8 Not breaking, verified unchanged

`EventStore`, `Cqrs`, `StreamFilter`, `Query`, `InlineProjection`, `AggregateVersion`,
`Event`, `Metadata`, `Aggregate`, `Compactable`, `Error`/`ErrorKind`/`ErrorStatus`, and the
whole of `es-replay-macros` (`define_aggregate!`, `query_events!`, `#[derive(Event)]`,
`#[derive(Urn)]`) are byte-identical in public surface.

## 4. Silent changes — compiles, behaves differently

These produce no compile error and no runtime error. They are the ones that cost you a
week if you miss them.

### 4.1 `PolicyStatus::lag` is a different number

| | `0.10.0` | `0.11.0` |
| --- | --- | --- |
| Definition | `MAX(global_position) - policy_cursors.position` | `Σ (stream head − policy's place)` over streams it is behind on |
| Counts | every event in the log, including whole streams the filter skips and positions a rolled-back write burned | unpassed rows in the streams this policy is behind on, with no burned positions |

Same name, same `i64`, usually a **smaller** number for the same operational state. Alert
thresholds tuned on the old value need re-baselining.

It is not a count of events that will be *delivered*: the new `lag` still includes events
the policy's filter will skip and the snapshot rows compaction writes, because those are
passed rather than delivered and until they are passed they are work
(`persistence/src/policy_status.rs`). What it drops is whole streams the policy is not
behind on, and global positions no transaction will ever fill. `streams_behind` is new and is the
field that separates "one stream a million events behind" from "a million streams one event
behind" — the same `lag`, very different problems.

### 4.2 `last_dead_letter_at` moves forward now

Reads `MAX(last_parked_at)` instead of `MAX(created_at)`. A command failing on every
delivery for a week used to show a week-old timestamp and now shows a recent one. Staleness
alarms built on it will stop firing for exactly the case they were meant to catch; alarm on
`dead_letter_count` instead.

### 4.3 A panicking reaction no longer kills its worker

On `0.10.0` a panic in `react` or in a dispatched handler unwound the worker task: that
policy stopped reacting for the life of the process, with no log line. Now every delivery
runs under `catch_unwind`, the panic is parked with `error_kind = 'Panic'`, an `error` line
names the policy and event, and the cursor advances past it.

A runbook of "the policy stopped, look for a crashed process" no longer detects anything.
Replace it with:

```sql
SELECT policy_name, count(*) FROM policy_dead_letters
WHERE error_kind IN ('Panic', 'Timeout') GROUP BY policy_name;
```

### 4.4 With no escalation hook, the process exits

A worker that dies outside the reaction path is restarted under a budget (count within a
sliding window, exponential backoff). Exhausting the budget calls the escalation hook, and
the **default hook is `std::process::exit(70)`** (`ESCALATION_EXIT_CODE`, `EX_SOFTWARE`).
Nothing like this happened on `0.10.0`, where the worker simply vanished.

If your supervisor does not restart on a non-zero exit, a wedged worker now takes the whole
process down instead of sitting dead. Decide which you want:

```rust
PolicyRunner::builder(cqrs)
    .with_worker_supervision(WorkerSupervision::default())
    .on_escalation(|escalation| {
        tracing::error!(policy = %escalation.policy, reason = ?escalation.reason, "worker escalated");
        // returning without exiting leaves the worker stopped and the process alive
    })
```

### 4.5 A lost stream-creation race no longer surfaces as `Internal`

Two concurrent first appends to a brand-new stream used to race on `streams_pkey`; the
loser got `Error::Internal`. It now defers, re-reads under lock and appends after the
winner. Code that special-cased `Internal` around first appends will stop seeing it. No
action needed unless that special case did something else too.

### 4.6 New `info` log volume from policies

`0.10.0` policies logged nothing at any level — idle and wedged were byte-identical. There
are now edge-triggered `info` lines: `"policy has work to do"`, `"policy is working through
its backlog"` (at most every 30s while draining), `"policy is caught up"` (with `events` and
`elapsed_ms`). Per-dispatch detail moved to `debug`, off by default. Volume is proportional
to state changes, not events.

## 5. Configuration

### New environment variables

| Variable | Default | Notes |
| --- | --- | --- |
| `REPLAY_DISPATCH_TIMEOUT_MS` | `30000` | Bounds one attempt at a *dispatched command*, not `Policy::react`. `0` or unparseable falls back to the default — it does **not** mean unbounded. |
| `REPLAY_STREAM_LOCK_WAIT_MS` | `30000` | `SET LOCAL lock_timeout` on the append path's `SELECT … FOR UPDATE` and on `compact`. `0` **disables** it. |
| `REPLAY_POLICY_RECONCILE_SECS` | `5` | Cadence of the scan that catches streams the discovery sweep passed while their write was still in flight. |

`REPLAY_READ_BATCH_SIZE`, `REPLAY_CHECKPOINT_BATCH_SIZE`, `REPLAY_MAX_CAUSATION_DEPTH` and
`REPLAY_PROJECTION_FLUSH_SIZE` keep their names and defaults. (`REPLAY_NOTIFY_CHANNEL` is
**not** an environment variable despite the name — it is an exported constant fixed at
`"replay_events"`, bound straight into `pg_notify`. Setting it in the environment does
nothing.) `REPLAY_READ_BATCH_SIZE` changed meaning: it is now a budget spent across every stream a
poll looks at, not a window on one ordered read.

### Two new ways to be cut off that did not exist before

- **Dispatch timeout.** It bounds each *dispatched command* — the aggregate's `handle`
  and the append behind it — not `Policy::react`. A command handler that legitimately
  takes longer than 30s now times out, retries, and eventually parks with
  `error_kind = 'Timeout'`. Raise it per policy:
  `PolicySettings::new().with_dispatch_timeout(Duration::from_secs(90))`.
  `react` itself is synchronous and is **not** covered: a `react` that blocks holds its
  worker with nothing to cut it loose, which is what the liveness surface is for.
- **Stream lock wait.** An append queued behind a long compaction of a very large stream now
  fails after 30s as `Unavailable` (retryable), where it used to wait indefinitely. Diagnose
  with `pg_locks`/`pg_stat_activity` on the named stream; raise with
  `PostgresEventStoreBuilder::stream_lock_wait(..)`.

## 6. New API

Nothing below requires a change; all of it is additive.

| Item | Purpose |
| --- | --- |
| `replay::ObservedEvent<E>` — `of`, `with_created`, `with_metadata` | the four fields a rule may read |
| `replay::AggregatePolicy` + `TargetedCommand<A>` | a policy whose commands all go to one aggregate: `type Target`, a `react` returning `(StreamId, Command)` pairs, and a `dispatch_metadata` hook run once per reaction |
| `PolicyRunnerBuilder::register_aggregate_policy_fn` / `..._with_metadata` | the closure registration with a declared target |
| `Dispatch::parts::<A>()` / `into_parts::<A>()` | borrow or take the `(StreamId, Command)` pair — how a *multi*-target policy's unit test asserts on the command without a runner |
| `Dispatch::target_stream_id()` / `command_name()` / `Debug` | dead-letter identity; `Debug` never prints the payload |
| `PolicySettings` | every policy knob, reachable from both registration paths |
| `PersistedEvent::of` + withers, `into_data()` | fixtures, and moving the payload out |
| `ScopedUrn::to_slug()` / `WithId::to_slug()` | the NSS up to the first `@`, borrowed, no allocation |
| `PolicyRunnerDaemon::liveness()` → `Vec<WorkerLiveness>` | `Leading / StandingBy / Restarting / Stopped / Unknown` per worker |
| `PolicyRunnerDaemon::stopped_workers()` | workers that exhausted their budget |
| `PolicyRunnerBuilder::with_worker_supervision`, `on_escalation`, `with_heartbeat`, `without_heartbeat`, `replica_id` | supervision and the durable heartbeat |
| `WorkerSupervision`, `Escalation`, `EscalationReason`, `Liveness`, `WorkerLiveness`, `StoppedWorker` | the liveness surface |
| `ESCALATION_EXIT_CODE`, `HEARTBEAT_CADENCE`, `HEARTBEAT_MIN_CADENCE`, `PANIC_ERROR_KIND`, `TIMEOUT_ERROR_KIND` | constants for hooks and queries |
| `PostgresEventStoreBuilder::stream_lock_wait(Duration)` | bound the append/compact lock wait in code |

`AggregatePolicy` is supplied a `Policy` impl by a blanket impl, so `register_policy` and
the runner are unchanged and a type implements one trait or the other, never both. It is
deliberately **not** in either prelude: importing both would make `policy.react(&event)`
ambiguous in a single-target unit test. Moving an existing `Policy` to it is optional.

`EscalationReason` and `Liveness` are `#[non_exhaustive]`; future variants there will not
break you. `DeadLetterRetry` is not, which is why `Superseded` broke your `match`.

`es-replay` gains a `chrono` dependency with no default features: `created` is a type-level
use with no clock call, and the crate still builds for `wasm32-unknown-unknown`.

## 7. Post-upgrade verification

```sql
-- Every event is numbered in its stream, and every stream agrees with its events.
SELECT count(*) FROM events WHERE stream_seq IS NULL;                         -- expect 0
SELECT count(*) FROM streams s
  WHERE s.stream_seq <> COALESCE((SELECT MAX(e.stream_seq) FROM events e WHERE e.stream_id = s.id), 0);
                                                                              -- expect 0

-- Every policy that had a position has places; none is unexpectedly at the beginning.
SELECT pc.name, count(psc.stream_id) AS streams, pc.discovered_through
FROM policy_cursors pc LEFT JOIN policy_stream_cursors psc ON psc.policy = pc.name
GROUP BY pc.name, pc.discovered_through;

-- The uniqueness key is valid, not a failed concurrent build.
SELECT indisvalid FROM pg_index WHERE indexrelid = 'idx_dead_letters_parked_command'::regclass;
                                                                              -- expect true
```

```rust
// Every worker settles. Poll: a worker is registered `Unknown` before its first
// election and may pass through `Restarting` on the way up, so a one-shot assert
// fails a healthy start. `Stopped` is terminal — fail on it immediately.
let deadline = Instant::now() + Duration::from_secs(60);
loop {
    let workers = daemon.liveness();
    if workers.iter().any(|w| w.liveness == Liveness::Stopped) {
        panic!("a worker exhausted its restart budget: {workers:?}");
    }
    if workers.iter().all(|w| matches!(w.liveness, Liveness::Leading | Liveness::StandingBy)) {
        break;
    }
    assert!(Instant::now() < deadline, "workers did not settle: {workers:?}");
    tokio::time::sleep(Duration::from_secs(2)).await;
}

// Lag is now per-stream; record the new baseline before re-arming alerts.
for status in status_store.list().await? {
    tracing::info!(policy = %status.name, lag = status.lag, streams_behind = status.streams_behind);
}
```

Re-baseline before re-arming: `PolicyStatus::lag`, `last_dead_letter_at` staleness, and any
`DeadLetterRetrySummary` threshold. Add, because nothing else will tell you a worker died:
an alarm on `policy_cursors.last_beat_at` older than three heartbeats, and on
`liveness = 'Stopped'`.

## 8. Rollback

There is no clean rollback past `0027` or `0034`. `0027` makes `events.stream_seq`
`NOT NULL`, which a `0.10.0` compaction cannot satisfy; `0034` drops
`policy_cursors.commit_txid` and renames `position`, which a `0.10.0` worker needs. Rolling
the binaries back without restoring the database leaves compaction and every policy poll
failing.

If you must go back: restore the pre-upgrade backup and replay the events written since
from your own source, or stay on `0.11.0` and fix forward. This is the reason for step 2 of
the pre-flight.
