# v0.14.0 — Delete streams with what Replay keeps about them

> Draft release notes, kept in the repo so the upgrade lands with the release. The
> published release page is assembled from this file (`docs/agents/release.md`).

## Highlights

**A stream can be deleted for good.** On `0.13.0` there was no API for it: a consumer that
hard-deletes an aggregate — a catalog entry whose stream id is a name slug, taken again
by the next entry of the same name — deleted Replay's rows by hand, and got it wrong in
ways only Replay can see. A Policy's **stream place** outlived the stream, so the
recreated stream, numbered from 1 again, was skipped up to wherever the Policy had got in
the old one; a **dead letter** whose triggering event was gone could never be retried and
aborted the bulk retry of its Policy; and a Policy running through the delete could write
either of them back (replay#292).

Now `PostgresEventStore::delete_streams` deletes the streams, every one of their events
(archived compaction versions included), every Policy's place in them and every dead
letter their events parked, in **one transaction**, and runs your closure in that same
transaction to delete your own read-model rows — inline projections included, since a
projection is handed events and a deletion is not one. A failure of either half undoes
both. It returns a `DeletedStreams` count. A stream created again under a deleted id is a
**new stream**: numbered from 1, delivered to Policies from its first event, applied to
inline projections like any other
([ADR-0033](https://github.com/funkode-io/replay/blob/v0.14.0/docs/adr/0033-a-deleted-stream-takes-what-replay-keeps-about-it.md)).

## ⚠️ Before you call `delete_streams`

**No migration.** `0.14.0` rolls over a `0.13.0` fleet like any patch: nothing changes
until the first deletion.

**Deploy `0.14.0` to every instance before the first call to `delete_streams`.** What
keeps a running Policy, a catch-up and a build from writing for a deleted stream lives on
*their* side, in this release. A Policy runner of an earlier release does not wait for a
deletion: it can re-insert its place (cursor) or park a dead letter for a stream after the
stream is deleted — a place that skips the recreated stream's first events, a dead letter
nothing can retry. An earlier release registering an inline projection for the first time
can likewise write view rows for a deleted stream. So:

1. **Roll every process to `0.14.0`** — every process that runs a Policy runner or
   registers an inline projection. Stopping the ones you do not upgrade counts.
2. **Only then call `delete_streams`.** Running Policies need not be stopped once they are
   on `0.14.0`.

For Data Loom: replace the hand-deletion runbook SQL with `delete_streams` only after the
`0.14.0` rollout has completed on every pod.

## Breaking changes

None. Every new item is additive and no signature changed.

### Behaviour changes to be aware of

- **A Policy's write of a first place and of a dead letter now waits for a deletion in
  flight**, and a deletion waits for appends, catch-ups and rebuilds in flight. Every wait
  is bounded by the [stream lock wait](https://github.com/funkode-io/replay/blob/v0.14.0/README.md#stream-lock-wait);
  one that runs out is `replay::ErrorKind::Unavailable`, to be retried.
- **A Policy's first start at `StartAt::Now` is refused as a conflict, and retried,** when
  it would seed a place for a stream being deleted.
- **A Policy checkpoint locks the events of its batch before their places**, so a
  checkpoint and a deletion queue rather than deadlock.
- **A poll spanning a deletion *and* a recreation can deliver some of the new stream's
  events twice**, the second time in order, as at-least-once delivery already allows.

Without a call to `delete_streams`, none of these waits ever happens.

## New API

### `PostgresEventStore::delete_streams`

```rust
pub async fn delete_streams<F>(
    &self,
    stream_ids: &[Urn],
    read_models: F,
) -> Result<DeletedStreams, replay::Error>
where
    F: for<'c> FnOnce(&'c mut sqlx::PgConnection, &'c [Urn])
            -> BoxFuture<'c, Result<(), replay::Error>>
        + Send;
```

Delete closed bank accounts together with the rows of your own `bank_account_balances`
view, in one transaction:

```rust
use replay_persistence::{DeletedStreams, PostgresEventStore};
use urn::Urn;

let closed = [
    BankAccountUrn::new("closed-41").expect("a valid id").into(),
    BankAccountUrn::new("closed-42").expect("a valid id").into(),
];

let deleted: DeletedStreams = store
    .delete_streams(&closed, |conn, ids| {
        Box::pin(async move {
            // `ids`: the streams the deletion locked, in the order you asked for them.
            // Their events can still be read here; the library deletes them after.
            let ids: Vec<String> = ids.iter().map(Urn::to_string).collect();
            sqlx::query("DELETE FROM bank_account_balances WHERE stream_id = ANY($1)")
                .bind(&ids)
                .execute(&mut *conn)
                .await
                .map_err(replay_persistence::db_error)?;
            Ok(())
        })
    })
    .await?;

tracing::info!(
    streams = deleted.streams,
    events = deleted.events,
    places = deleted.places,
    dead_letters = deleted.dead_letters,
    "bank accounts deleted"
);
```

With no read model of your own, pass a closure that does nothing:

```rust
let deleted = store
    .delete_streams(&closed, |_, _| Box::pin(async { Ok(()) }))
    .await?;
```

What it does, in short:

- **Only streams that exist when the deletion locks them** are deleted and handed to the
  closure. An id with no stream is ignored, even if a stream is created under it while
  the deletion runs. An empty slice returns at once without calling the closure; a
  non-empty one naming no stream calls it with an empty slice.
- **The closure runs before the library's own deletes**, on the deletion's connection, so
  a read model keyed by something inside the streams can still find its rows. An `Err`
  from it — or from any step — rolls the whole deletion back and is returned.
- **Dead letters are deleted, not archived:** a deletion is a cleanup, and a dead letter
  whose event is gone can never be retried. Dead letters already archived stay as
  history; a dead letter *addressed to* a deleted stream by an event of another stream
  stays, since its trigger still exists.
- **Lock waits**, the closure's statements included, are bounded by the stream lock wait;
  running out is `ErrorKind::Unavailable`:

```rust
match store.delete_streams(&closed, |_, _| Box::pin(async { Ok(()) })).await {
    Ok(deleted) => { /* gone */ }
    Err(error) if error.kind() == replay::ErrorKind::Unavailable => { /* busy: retry */ }
    Err(error) => return Err(error),
}
```

`delete_streams` is on `PostgresEventStore` only, not on the `EventStore` trait: the
in-memory store keeps no places, no dead letters and no transaction to join.

### `DeletedStreams`

What a deletion removed. Exported from the crate root and from
`replay_persistence::prelude`.

```rust
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
pub struct DeletedStreams {
    pub streams: u64,      // the ids asked for that named a stream
    pub events: u64,       // archived compaction versions included
    pub places: u64,       // one per Policy that had a place in a stream
    pub dead_letters: u64, // parked dead letters whose triggering event was deleted
}
```

## Migration

No code changes and no database migration are required. Deploy `0.14.0` to every
instance before the first `delete_streams` call (above).

> **Rollout rule (ADR-0033):** call `delete_streams` only once every process that runs a
> Policy runner or registers an inline projection runs `0.14.0`, or is stopped. An older
> Policy runner can re-insert a place (cursor) or park a dead letter for a stream after
> its deletion.
