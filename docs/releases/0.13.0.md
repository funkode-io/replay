# v0.13.0 — Inline projections survive a rolling deploy

> Draft release notes, kept in the repo so the upgrade lands with the release. The
> published release page is assembled from this file (`docs/agents/release.md`).

## Highlights

**An inline projection catches up on appends that did not apply it.** On `0.12.0` an
inline projection was applied only by the process that appended, and only if that process
had registered it. During a rolling deploy that is not every process: an old pod without a
new projection appended events the projection never saw, an old pod running an older
version applied its old logic to the view the new version had just rebuilt, and appends
committed while `build()` replayed were applied by nobody (#162). Nothing repaired the gap
until the next version bump (replay#289).

Now every append records, per projection version, that its transaction applied the
projection, and the store **catches up** each projection on the events of every other
transaction — once per projection version, in `global_position` order, whichever process
appended them ([ADR-0032](https://github.com/funkode-io/replay/blob/v0.13.0/docs/adr/0032-an-inline-projection-catches-up-on-transactions-that-did-not-apply-it.md)):

- **at startup**, in `build()`;
- **on a cadence**, from a background task `build()` starts when a projection is
  registered (default 60 s);
- **on demand**, with `PostgresEventStore::catch_up_projections()`.

What has been applied is tracked by the transaction that wrote each event (its commit
stamp), never by a position, so a late write is still caught up.

**A projection can declare the event types it handles.** `InlineProjection::event_types()`
narrows the rebuild replay, the catch-up and the live append to those types before
anything is deserialized. One downstream rebuild over a long, mixed log went from ~35 s to
~1 s.

## ⚠️ Before you deploy

**Run migration `0038_projection_catch_up` (in `persistence/tests/migrations/`) before
starting `0.13.0`.** This release reads and writes what it adds on its first append or
`build()`.

| Migration | What it does | Notes |
| --- | --- | --- |
| `0038_projection_catch_up` | `projections.caught_up_below xid8` and `caught_up_version INTEGER`, both nullable; new table `projection_applied_transactions (projection, version, txid)` | Additive and instant. `0.12.0` never reads either, so migrate while it runs, then roll the processes. |

### Rolling out over a `0.12.0` fleet

For a consumer such as Data Loom:

1. **Migrate first.** Run the Replay migrations (through `0038`) while `0.12.0` pods are
   still serving. Nothing they do changes.
2. **Roll the pods.** The first `0.13.0` `build()` finds no catch-up horizon on each
   existing projection and **adopts** the log as it stands: history before the upgrade is
   not replayed. From then on, events that `0.12.0` pods still append — with the
   projection registered or not, since they write no applied marks — are caught up by the
   `0.13.0` pods within one catch-up interval.
3. **Non-idempotent handlers: stop, then start.** A projection whose `handle` accumulates
   (a running balance) would count an event a `0.12.0` pod applied live a second time
   when a `0.13.0` pod catches it up. Take this upgrade as a stop-then-start deploy for
   such projections. Upsert-style handlers that set values can roll.
4. **Quiesce writers without the projection during the first build.** The guarantee starts
   at the adoption in the first upgraded `build()`: an append by a process *without* the
   projection that commits while that build runs can be adopted without being applied.
5. **Missed history before the upgrade** is still repaired the old way: bump the
   projection's version so `build()` rebuilds it.

After this release, every version bump during a rolling deploy works the same way: the
newer version re-applies what an older one applied live, so handlers should be upserts
that let the newer logic win (or the bump should be stop-then-start).

**Logical restores** (`pg_dump`/`pg_restore` into another cluster) now need three
statements before the first append, because commit stamps and horizons are
cluster-local transaction ids; see the README section *Rolling deploys: catching up on
appends that did not apply it*. A physical restore or replica promotion needs nothing.

## Breaking changes

None. The new trait method has a default and every new item is additive.

### Behaviour changes to be aware of

- **Every append through a store with registered projections writes one row per
  projection** to `projection_applied_transactions`, in the append transaction. Each
  catch-up round deletes the rows below its horizon.
- **`build()` starts a background task** when at least one projection is registered. It
  holds a weak reference to the store and stops when the store is dropped. Disable it with
  `Duration::ZERO` or `REPLAY_PROJECTION_CATCH_UP_SECS=0`.
- **A caught-up event can arrive after a later event of the same stream** was applied
  live. A handler whose result depends on order should guard on a value its view keeps.
- **Two processes building the same projection now queue** on its advisory lock instead
  of failing on a serialization error or duplicate key.

## New API

### `PostgresEventStoreBuilder::projection_catch_up_interval`

How often the background task catches every registered projection up. Overrides
`REPLAY_PROJECTION_CATCH_UP_SECS`; default 60 s; `Duration::ZERO` disables the task
(startup and on-demand catch-up still run).

```rust
use std::time::Duration;
use replay_persistence::PostgresEventStore;

let store = PostgresEventStore::builder(pool)
    .projection_catch_up_interval(Duration::from_secs(30))
    .build()
    .await?;
```

| Setting | Store override | Env var | Default |
|---------|----------------|---------|---------|
| Interval between background catch-ups | `projection_catch_up_interval(d)` | `REPLAY_PROJECTION_CATCH_UP_SECS` | `60` s; `0` disables |

### `PostgresEventStore::catch_up_projections`

Catch every registered projection up now and return how many events were read. Waits for
each projection's advisory lock rather than skipping; a projection whose stored version is
not this process's code version is skipped.

```rust
// e.g. after a bulk import, before reading the views
let read: u64 = store.catch_up_projections().await?;
```

### `InlineProjection::event_types`

Declare the event `type`s a projection handles, as `Event::event_type` wrote them.
Defaults to `None` (deserialize-or-skip, as before).

```rust
impl InlineProjection for BankAccountBalances {
    type Exec = sqlx::PgConnection;
    type Event = BankAccountEvent;

    // …name, version, init, handle as before…

    fn event_types(&self) -> Option<Vec<String>> {
        Some(vec!["Deposited".into(), "Withdrawn".into()])
    }
}
```

List every type the projection's `Event` can hold: a type left out never reaches `handle`.
